## 🧠 Логіка проєкту (що де живе)

Застосунок складається з тонкого бекенду (`app/`, Python + FastAPI) та
фронтенду без build-кроку (`static/`, vanilla JS). Усі обчислення клімату —
на бекенді; фронтенд лише малює.

### `app/ha_client.py` — клієнт Home Assistant REST API

- Тягне `/api/states` з вашого Home Assistant за токеном з `data/` (у репо не потрапляє).
- Функції **парсингу — чисті** (`parse_states` та ін.): приймають payload, повертають
  `{entity_id: {metric: value}}`. Вони юніт-тестуються проти записаних фіксчурів,
  без мережі. Мережеві обгортки ніколи не піднімають виняток угору — при збої
  повертають порожні дані, щоб дашборд лишався живим.
- Розпізнає метрики за `unit_of_measurement`: `°C` → temperature, `%` → humidity,
  `kWh` → energy, `ppm` → co2, `ppb` → voc.

### `app/climate.py` — психрометрія: точка роси та ризик цвілі

Точка роси рахується за **формулою Магнуса (Magnus-Tetens)** — стандартною
апроксимацією тиску насиченої водяної пари:

```
γ(T, RH) = ln(RH/100) + (a·T) / (b + T)
Td = (b·γ) / (a − γ)
```

де `a = 17.62`, `b = 243.12 °C` (коефіцієнти для діапазону −40…+50 °C над водою),
`T` — температура повітря в °C, `RH` — відносна вологість у %.

Інтуїція: точка роси — це температура, до якої треба охолодити повітря, щоб
пара почала конденсуватися. Чим ближче `Td` до фактичної температури
холодної поверхні (стіна, склопакет), тим вища ймовірність конденсату та цвілі.

`mold_risk(T, RH)` — якісна шкала на основі цих самих величин:

- `high` — RH ≥ 70 % при T < 20 °C (класична зона конденсату на холодній поверхні);
- `medium` — RH ≥ 65 % (наближення до небезпечної зони);
- `low` — решта.

Якщо змінюєте ці пороги — оновіть і тест, і підказку в UI (`mold_title` в i18n).

### `app/openmeteo.py` — зовнішня погода

Клієнт безкоштовного Open-Meteo API (без ключа): історія температури
(`archive-api`) та 48-годинний прогноз (`forecast`). Як і в `ha_client`,
парсери чисті й протестовані, фетчери ніколи не падають — при проблемах
із мережею повертають порожню серію, тож дашборд працює офлайн
(без зовнішніх даних на графіках).

### `app/cache.py` — SQLite-кеш історії + мемоізація агрегатів

- Таблиця `readings(room, metric, ts, value)` — уся довга історія локально,
  щоб не питати HA за кожним кліком. Плюс `annotations` для міток на таймлайні.
- Агрегати (`hourly_mean`, `heatmap_matrix`, `hourly_since`, `heatmap_since`)
  **мемоізовані** в пам'яті за ключем `(кімната, метрика, since, кількість точок)`.
  Повторні запити до `/api/timeline` і `/api/heatmap` у межах години не перечитують БД.
- Будь-який запис скидає кеш (`_invalidate`) — інваріант: після запису
  агрегати завжди перераховуються зі свіжих даних. Якщо додаєте новий шлях
  запису в кеш — не забудьте інвалідацію, інакше тести це впіймають
  (є регресійний тест на біт-ідентичність агрегатів).

### `app/demo_data.py` — детермінізм критично важливий для тестів

Демо-генератор створює синтетичну, але правдоподібну історію (90 днів × кімнати ×
метрики). Ключове правило: **той самий `(кімната, день)` завжди дає той самий
годинниковий ряд**. Детермінізм тримається на:

- стабільних per-room офсетах, похідних від імені кімнати (`_room_profile`);
- псевдошумі з `random.Random(f"{room}|{day}|…")` — seed-рядок, а не глобальний стан;
- `lru_cache` на шумі — це оптимізація (~3.7× на seed), яка **не змінює значень**
  (закріплено регресійним тестом).

Наслідок: тести, скріншоти й бенчмарки відтворювані. Якщо змінюєте формули
генератора — серії змінюються; регресійний тест скаже вам це голосно.

### Досвід продуктивності: `docs/PERFORMANCE.md`

Перед тим як «оптимізувати» щось у `demo_data` / `cache.py`, прочитайте
`docs/PERFORMANCE.md` — там задокументовано повний цикл: симптом
(pytest 87.6 s), cProfile-знахідки (топ-3 гарячі місця), база
`scripts/bench.py` «до/після» і що саме було зроблено. Головні уроки:

- профілюйте перед тим, як гадати (`scripts/profile_hot.py`, `pytest --durations=15`);
- `random.Random(str-seed)` на кожну точку — найдорожча операція в seed;
- один `executemany` б'є тисячі окремих `INSERT`;
- мемоізація агрегатів безкоштовно пришвидшує повторні запити, але **обов'язково**
  з інвалідацією після записів.

## 🔧 Середовище та тести

```bash
python -m venv .venv && . .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m pytest -q          # має бути зеленим
python -m app.main           # запуск сервера
```

### Як писати ШВИДКІ тести

Кожен тест із фіксчуром `client` засіює демо-історію у свою тимчасову БД.
Повний обсяг (90 днів) — це ~43 200 точок; у тестах досить значно меншого.

- За замовчуванням фіксчур засіює **32 дні** (`tests/conftest.py`).
- Якщо вашому тесту треба відтворити повний обсяг або інший горизонт —
  перевизначте змінну оточення:

  ```bash
  CLIMATE_CANVAS_TEST_DAYS=90 python -m pytest -q tests/test_cache.py
  ```

- Правила: не засіюйте дані вручну там, де вистачить фіксчура; не збільшуйте
  `TEST_DEMO_DAYS` «про всяк випадок»; агрегатні тести перевіряйте на малих
  вікнах (7–32 дні). Повний прогін має лишатися в межах ~15 s.

## ➕ ЯК ДОБАВИТИ МЕТРИКУ (на прикладі CO₂/VOC)

Це найпоширеніший тип фічі. CO₂ і VOC пройшли саме цей шлях:

1. **Парсинг** — `app/ha_client.py`, `parse_states`: додати розпізнавання
   юніта (`ppm` → `co2`, `ppb` → `voc`) у цикл по `unit_of_measurement`.
2. **Конфіг кімнати** — `app/config.py`: додати поле сутності
   (`co2_entity`, `voc_entity`), щоб користувач прив'язав сенсор у налаштуваннях.
3. **API** — `app/main.py`: розширити regex-патерни `Query(..., pattern=...)`
   (включно з `HEAT_METRICS`) та `enrich()`/`/api/rooms`, щоб метрика
   потрапляла у відповіді.
4. **Кеш** — `app/cache.py` зберігає будь-які `(room, metric, ts, value)`,
   тож окремих змін зазвичай не треба; перевірте, що запис йде через
   `add_readings` (агрегати й інвалідація працюють автоматично).
5. **UI** — `static/app.js`: лінії таймлайну/теплова мапа + пункт вибору метрики.
6. **i18n** — `static/i18n.js`: ключ `metric_<name>` в обох словниках
   (`uk` і `en`) — одразу обидва, не «додам англійську пізніше».
7. **Тести** — юніт-тест парсера з фіксчуром payload + інтеграційний тест
   endpoint'а через фіксчур `client` (демо-дані не містять нової метрики —
   засійте її в тесті явно).
8. **CHANGELOG.md** — рядок у `[Unreleased]`.

## 🌿 Гілки

- **`master`** — стабільна гілка: бекенд + веб-UI, зелений pytest, сюди йдуть усі
  зміни коду/документів. Кожен коміт має бути робочим.
- **`mobile/android-ios`** — мобільний порт (Capacitor 6): `android/`, `ios/`,
  splash з налаштуванням адреси HA-сервера + кнопка демо-режиму, CI-збірки
  (`android-build.yml`, `ios-build.yml`), `MOBILE.md`. Утримується поверх
  `master` (rebase/merge з master регулярно); бекенд-зміни робляться в master
  і потрапляють сюди лише через merge — **не правте бекенд напряму
  в мобільній гілці**.
- Нові фічі: короткоживучі гілки від `master` → PR у `master`.

## 🔀 PR і коміти

- Одна фіча/фікса = один PR; тіло коміту/PR пояснює «чому», а не «що».
- Додайте або оновіть pytest-тести (кожна фіча покрита тестами).
- Стиль комітів: `type: короткий опис` (`feat:`, `fix:`, `test:`, `perf:`,
  `docs:`, `mobile:`, `ci:`). Приклади з історії: `perf: cache demo noise per (room, day)`,
  `test: client fixture seeds 32 demo days`.
- Не комітьте `data/` (там токен і кеш), `.env`, `rooms.json`.

## 🌐 i18n

- Усі UI-рядки — у `static/i18n.js`, словники `uk` та `en`; динамічні рядки —
  через `I18N.t()`.
- У HTML-розмітці використовуються атрибути `data-i18n` / `data-i18n-ph` /
  `data-i18n-title`.
- Мова визначається автоматично за браузером і зберігається у `localStorage`.
- **Російську локалізацію не додавати** — це свідоме рішення власника проєкту.
  І жодних нових мов «на швидку руку»: спершу issue.

## 🚦 Чекліст перед PR

- [ ] `python -m pytest -q` зелений (~15 s);
- [ ] нові рядки UI є в обох словниках (`uk`, `en`);
- [ ] регресійний тест на агрегати не впав (не зламали мемоізацію/детермінізм);
- [ ] CHANGELOG.md оновлено;
- [ ] у diff немає `data/`, токенів, згадок російської локалізації.

Перед великими змінами відкрийте issue і обговоріть підхід.
